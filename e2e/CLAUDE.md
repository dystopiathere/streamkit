# @streamkit/e2e

## Назначение
Сквозные сценарии в настоящем браузере. Проверяют то, что недоступно юнит- и
feature-тестам: что собранный оверлей действительно устанавливает соединение и
отрисовывает событие, прошедшее через Redis и сокет.

## Технологии
Playwright, Chromium.

## Ключевое решение

Тесты гоняются по **собранным** приложениям, а не по dev-серверам. Переменные
`VITE_*` вшиваются в бандл при сборке, и проверять надо именно тот артефакт,
который поедет в прод — иначе ошибка конфигурации сборки обнаружится после
деплоя. Playwright сам поднимает три сервера: API, дашборд, оверлей.

## Правила

- Один воркер: тесты делят одну базу, параллельный прогон сделает результат
  случайным.
- Уникальные email на каждый прогон (`Date.now()`): база между прогонами не
  чистится.
- Селекторы — по роли и тексту, как их видит пользователь. `data-testid`
  оставлен только для карточки оповещения, у которой нет осмысленной роли.
- Строгий режим Playwright не прощает неоднозначных селекторов: «тест» находится
  и в бейдже, и внутри «Тестовый зритель» — нужен `{ exact: true }`.
- **Локально тесты переиспользуют уже запущенные серверы** (`reuseExistingServer`),
  а у `pnpm dev` боевой лимит: десять запросов к `/auth` в минуту с IP. Полный
  прогон его исчерпывает, и тест, перезагрузивший страницу, вылетает на форму
  входа — это 429 на обновлении токена, а не поломка сессии. Либо запускайте
  API с `THROTTLE_AUTH_LIMIT=100000`, либо гоняйте файлы тестов по одному с
  перерывом в минуту. В CI лимит поднимает `playwright.config.ts`.

## Запуск

```bash
pnpm build                          # обязательно: тесты идут по dist
pnpm --filter @streamkit/e2e test
pnpm --filter @streamkit/e2e test:ui   # интерактивный режим
```

Нужны запущенные PostgreSQL и Redis и накатанные миграции.
