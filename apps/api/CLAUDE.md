# @streamkit/api

## Назначение
Бэкенд целиком: HTTP API, WebSocket-шлюзы и фоновый процесс. Две точки входа на
одном коде — `src/main.ts` (API) и `src/worker.ts` (фон).

Воркер не вынесен в отдельный пакет намеренно: ему нужны те же доменные сервисы
(приём событий, дедупликация, шифрование токенов), и третий пакет дал бы либо
дублирование, либо искусственный слой ради структуры папок.

## Технологии
NestJS 11 (Express), Prisma 7 + PostgreSQL, ioredis, Socket.IO + redis-adapter,
`@node-rs/argon2`, otplib, Zod для валидации, pino для логов, Vitest + supertest.

## Ключевые решения

**Ротация refresh-токенов с детектом переиспользования.** Каждое обновление
выпускает новый токен и гасит старый. Предъявление погашенного токена означает
утечку копии — гасим всё семейство. Гонка двух параллельных обновлений решена
атомарным `updateMany` с условием `revokedAt: null`.

**Дедупликация в два слоя.** Быстрый `SET NX` в Redis до записи в БД плюс
уникальный индекс `(provider, externalId, userId)`. Redis теряет ключи при
перезапуске, индекс — нет. Дубль алерта видят зрители, поэтому «сначала показать,
потом разобраться» не подходит.

**Шина вместо прямых вызовов.** Виджеты публикуют «конфиг изменился», ничего не
зная о шлюзе; шлюз ничего не знает о сервисе виджетов на уровне модулей. Так нет
цикла импортов и не нужен `forwardRef`, а события доходят из воркера, где
сокет-сервера нет вовсе.

**Рассылка через `.local`.** Фан-аут между процессами делает шина, поэтому шлюз
шлёт только своим сокетам. Иначе каждый инстанс размножил бы одно событие.

## Правила

- Валидация входа — схемами из `@streamkit/contracts` через `zodBody(...)`.
  `class-validator` в проекте нет и добавлять его не нужно.
- Владение объектом проверяется в каждом методе сервиса; чужое отдаёт 404.
- Ответы об ошибках аутентификации одинаковы для всех причин: разные тексты
  превращают вход в оракул для перебора адресов.
- Любое действие с безопасностью пишется в `AuditService`. Падение записи аудита
  не должно ломать основной сценарий.
- Интерфейсов интеграции три, и выбор простой. Площадка присылает события сама,
  соединение на пользователя — `DonationConnector` плюс запись в
  `ConnectorManager`. У площадки надо спрашивать — `PlatformProvider` плюс
  запись в `PlatformRegistry`. Присылает сама, но одним соединением на много
  каналов — `ChatSource`. Почему не один интерфейс: `docs/adr/0006` и `0009`.
- Долгоживущий ресурс, который обязан быть один на кластер, берётся АРЕНДОЙ
  (`RedisLock.acquire` + `renew`), а не `withLock`. Разница в смысле: `withLock`
  про задачу, которая обязана выполниться один раз и завершиться; аренда — про
  ресурс, который кто-то один обязан держать.
- Внешние вызовы идут через `HttpClient`, а не голый `fetch`: у него есть
  таймаут, повторы и различение «токен мёртв» / «слишком часто» / «сломалось».
- **Права в токене LiveKit выставляет только `LiveKitTokens`.** Роль участника —
  префикс идентичности (`host:`, `guest:`, `overlay:`), который ставит сервер;
  атрибутам и метаданным клиента не доверяем. Действия над участниками —
  только над гостями.
- **Виджет гостей ссылается только на свою комнату** — проверка в
  `WidgetsService` при создании и правке и ещё раз при выдаче доступа
  оверлею. Без неё чужой `roomId` в своём виджете открывал бы видео чужой
  приватной комнаты по собственной ссылке OBS.
- **Каждый вход в комнату проверяется по вебхуку LiveKit** (`/api/livekit/webhook`,
  `RoomsService.enforceJoin`). Выданный токен не отзывается, и правило «кому
  можно в комнату» обязано совпадать с правилом выдачи токенов: меняешь одно —
  меняй другое.
- Медиасервер в интеграционных тестах подменяется через `ROOM_MEDIA_SERVER`;
  хранилища — никогда. Путь через настоящий LiveKit закрыт сквозным тестом.
- Задача по расписанию, которая обязана выполниться один раз на кластер,
  оборачивается в `RedisLock.withLock`.
- **Деньги не держатся на блокировке.** Продление подписки идёт под
  `withLock`, но от двойного списания защищают ключ идемпотентности в запросе
  к ЮKassa и уникальный индекс попытки: блокировка может истечь посреди ответа.
- **Уведомлению платёжного сервиса не верим.** Статус и сумма — только из
  переспроса (`BillingService.syncPayment`), применение — условным переходом из
  `PENDING` в одной транзакции с продлением.
- Доступ к приватным комнатам проверяет `BillingService.roomsAccess` везде, где
  он выдаётся: создание, вход стримера, гостя, оверлея и вебхук входа. Меняешь
  одно — проверь остальные.
- Платёжный шлюз в интеграционных тестах подменяется через `PAYMENT_GATEWAY`,
  сквозной прогон ходит в `e2e/fake-yookassa.mjs`. Почта — через `MAILER`.
- **Продление не списывается без письма о списании** (`renewalNoticeFor` =
  текущий конец периода, отправлено ≥3 дней назад): так обещает оферта. Нет
  почты — нет и списаний. Всё, что меняет сумму продления (смена периода, цена),
  сбрасывает отметку письма.
- **Сумма продления — `Subscription.renewalAmountMinor`, а не `PLAN_PRICES`.**
  Новая цена действующим подписчикам — только после письма за 30 дней.
- Письма — только текстом (`MailMessage.text`): в них имя и подпись способа
  оплаты, и HTML дал бы им стать разметкой.
- Сроки хранения в `MaintenanceService` совпадают с таблицей в политике
  конфиденциальности. Меняешь одно — меняй другое и версию документа.

## Проверка

```bash
pnpm --filter @streamkit/api typecheck
pnpm --filter @streamkit/api test        # юнит, без внешних зависимостей
pnpm --filter @streamkit/api test:int    # интеграционные: нужны PostgreSQL и Redis
```

Интеграционные тесты поднимают настоящее приложение поверх настоящих БД и Redis.
Моки хранилищ не используются: проверяются именно уникальные индексы, каскады,
транзакции и атомарность — то, что мок воспроизводит неверно.

## Известные ограничения

- Подписка не проверена на тестовом магазине ЮKassa: формат чека (`quantity`,
  `vat_code`), сохранение способа оплаты и список возвратов написаны по
  документации. SMTP Postbox не проверен на живом домене.
- Возврат, пропущенный уведомлением, дочистка не подбирает: список возвратов
  переспрашивается только по уведомлению `refund.*`.
- Коннектор DonationAlerts написан по документации и **не проверен на живом
  аккаунте**: нужен зарегистрированный клиент OAuth. Рабочий путь приёма событий
  сейчас — собственный вебхук, он покрыт тестами.
- Коннектор Twitch написан по спецификации Helix и **не проверен на живом
  аккаунте**: приложение Twitch пока не зарегистрировано. YouTube проверен.
- `findDispatchTargets` ходит в БД на каждое событие. При росте нагрузки —
  кэшировать в Redis с инвалидацией по шине.
- Токены площадок с провайдером метрик продлеваются автоматически. У донат-
  площадок продлевать нечем: провайдера для них нет, и истёкший доступ выключает
  источник с причиной в `DonationSource.disabledReason` и записью в аудит.
  Показать причину пока негде: списка источников в дашборде нет, есть только
  выпуск секрета вебхука.
- У цели и топа донатеров нет кэша: прогресс считается запросом на каждое
  событие и на каждое подключение оверлея. При десятках тысяч событий на
  пользователя это стоит заметить (см. docs/adr/0008 — размен сознательный).
- Чат YouTube не реализован и не будет до смены модели квоты:
  `liveChatMessages.list` стоит единицу на опрос при обязательной частоте раз в
  пять секунд, то есть ~4300 единиц за шестичасовой эфир ОДНОГО стримера при
  суточном лимите 10 000 на весь проект (docs/adr/0007 и 0009).
- Чат Twitch при гибели владельца аренды пропадает до тридцати секунд, пока
  ключ не истечёт. Для чата это сознательный размен; для донатов он был бы
  неприемлем — там дедупликация по идентификатору события, а не аренда.
- Состав каналов чата сверяется опросом БД раз в десять секунд: механизма
  команд воркеру в проекте нет. Новый виджет начинает показывать чат не
  мгновенно, а в пределах такта.
- Поток чата подрезан двадцатью сообщениями в секунду на канал. Виджет
  показывает два десятка строк, и остальное всё равно никто не прочитает.
- Гость, удалённый с отзывом ссылки и вошедший обратно сохранённым токеном,
  проводит в комнате время доставки вебхука — доли секунды, — прежде чем
  `enforceJoin` его выгонит. Отозвать сам токен LiveKit 1.13 не умеет
  (docs/adr/0010).
