# infra

## Назначение
Сборка образов и запуск окружений.

## Состав

| Файл | Для чего |
|---|---|
| `docker/compose.dev.yml` | PostgreSQL, Redis, LiveKit (`--dev`) и Mailpit (письма на :8025) для локальной разработки |
| `docker/compose.yml` | Полный стек: то же, что поедет в прод |
| `docker/api.Dockerfile` | Образ API и воркера — один код, разные команды |
| `docker/web.Dockerfile` | Статика дашборда и оверлея, выбор через `--build-arg APP` |
| `docker/nginx.conf` | Отдача статики |
| `docker/security-headers.conf` | Заголовки безопасности и CSP — подключаются в КАЖДЫЙ `location` со своим `add_header` |
| `docker/permissions-*.conf` | Permissions-Policy по приложению: дашборду камера и микрофон, оверлею — нет |
| `livekit/README.md` | Медиасервер комнат: конфигурация в `LIVEKIT_CONFIG` внутри compose |
| `yandex-cloud/terraform` | Облако прода: сеть, ВМ, управляемые PostgreSQL и Valkey, реестр, Lockbox, DNS |
| `yandex-cloud/app` | Compose, Caddyfile и скрипт выкатки ВМ приложений |
| `yandex-cloud/livekit` | Compose, выкатка и продление сертификата TURN на ВМ медиасервера |
| `yandex-cloud/README.md` | Порядок подготовки облака, GitHub и первой выкатки |

## Почему приложения не в dev-compose

На Windows bind-mount со структурой симлинков pnpm работает медленно и
ненадёжно, а hot-reload через контейнер добавляет секунды на каждое сохранение.
Поэтому базы — в Docker, код — на хосте. Полная сборка проверяется отдельно
через `compose.yml`, который повторяет прод.

## Правила

- Миграции выполняет отдельный одноразовый контейнер, а не старт API: при
  нескольких репликах несколько процессов начали бы мигрировать базу разом.
- Образы запускаются от непривилегированного пользователя `node`.
- `/healthz` не трогает зависимости: если упал PostgreSQL, перезапуск всех
  контейнеров API сделает только хуже. Для вывода из балансировки есть `/readyz`.
- **Журнал nginx — без строки запроса и Referer**: в них токен оверлея из ссылки
  OBS. `location` для `/legal/` — только файлы `.md`, страницы документов — SPA.
- **Umami с основного домена — только `/u/script.js` и `/u/api/send`.** Весь
  Umami по префиксу открыл бы его вход и API в обход пароля `stats.<домен>`.
  Интерфейс — на `stats` за `basic_auth`; ключи Umami из секрета приложения
  deploy.sh в окружение API не пускает. После пароля пропуск — httpOnly-cookie
  `stats_gate`: заголовок `Authorization` занят токеном самого Umami.
  Выдача cookie — внутри `route`, строго после `basic_auth`.
- **Расширения PostgreSQL — только блоком `extension` в Terraform.** Владелец базы
  в управляемом кластере их не включает: Umami на `CREATE EXTENSION pgcrypto`
  падал при старте.
- **Вебхук LiveKit снаружи закрыт в Caddy**: медиасервер ходит на внутренний
  адрес API, а открытая ручка без лимита писала бы аудит на каждую подделку.
- **Заголовки проверяются `curl -I` по пути страницы**, а не чтением конфига:
  `add_header` в `location` отменяет наследование заголовков сервера, и CSP
  не доходила до страниц с первого образа, хотя в конфиге стояла.
- `VITE_*` и `CSP_CONNECT_EXTRA` вшиваются при сборке образа. Смена адреса API требует пересборки —
  это ограничение любой статики, и лучше знать о нём здесь.
- Секреты не хранятся в образах и не коммитятся. В проде — Lockbox, ВМ читает
  его своим сервисным аккаунтом при каждой выкатке; в CI — только ключ публикации
  образов и ключ выкатки.
- **API и воркер получают одно и то же окружение** — якорем в `compose.yml` и
  одним `.env` в проде. Урезанное окружение воркера молча выключало продление
  подписки и обновление токенов площадок.
- **Миграции — отдельный образ** (`--target migrate`): в рантайм-образе нет ни
  CLI Prisma, ни npx.
- `VITE_API_URL` — origin API без `/api`, пустой — «тот же хост».
- **Прод выкатывается только workflow «Выкатка»** с тегом-sha из `main`. Руками
  на ВМ — только разбор аварии; изменения, сделанные руками, следующая выкатка
  перезапишет.

## Запуск

```bash
docker compose -f infra/docker/compose.dev.yml --env-file .env up -d
docker compose -f infra/docker/compose.yml --env-file .env up --build
```
