# infra

## Назначение
Сборка образов и запуск окружений.

## Состав

| Файл | Для чего |
|---|---|
| `docker/compose.dev.yml` | PostgreSQL, Redis, LiveKit (`--dev`) и Mailpit (письма на :8025) для локальной разработки |
| `docker/compose.yml` | Полный стек: то же, что поедет в прод |
| `docker/api.Dockerfile` | Образ API и воркера — один код, разные команды |
| `docker/web.Dockerfile` | Статика дашборда, оверлея и админки, выбор через `--build-arg APP` |
| `docker/nginx.conf` | Отдача статики |
| `docker/security-headers.conf` | Заголовки безопасности и CSP — подключаются в КАЖДЫЙ `location` со своим `add_header` |
| `docker/permissions-*.conf` | Permissions-Policy по приложению: дашборду камера и микрофон, оверлею и админке — нет |
| `livekit/README.md` | Медиасервер комнат: конфигурация в `LIVEKIT_CONFIG` внутри compose |
| `yandex-cloud/terraform` | Облако прода: сеть, ВМ, управляемые PostgreSQL и Valkey, реестр, Lockbox, DNS |
| `yandex-cloud/app` | Compose, Caddyfile и скрипт выкатки ВМ приложений |
| `yandex-cloud/livekit` | Compose, выкатка и продление сертификата TURN на ВМ медиасервера |
| `yandex-cloud/README.md` | Порядок подготовки облака, GitHub и первой выкатки |

## Почему приложения не в dev-compose

На Windows bind-mount со структурой симлинков pnpm работает медленно и
ненадёжно, а hot-reload через контейнер добавляет секунды на каждое сохранение.
Поэтому базы — в Docker, код — на хосте. Полная сборка проверяется отдельно
через `compose.yml`, который повторяет прод.

## Правила

- Миграции выполняет отдельный одноразовый контейнер, а не старт API: при
  нескольких репликах несколько процессов начали бы мигрировать базу разом.
- Образы запускаются от непривилегированного пользователя `node`.
- `/healthz` не трогает зависимости: если упал PostgreSQL, перезапуск всех
  контейнеров API сделает только хуже. Для вывода из балансировки есть `/readyz`.
- **`/` отдаёт `landing.html`, если он есть** — главную со статическим снимком
  для поисковиков; остальные адреса SPA — `index.html`. У админки и оверлея
  файла нет, и `try_files` падает на прежний index.html. `.webmanifest` отдаётся
  отдельным `location`: в mime.types nginx 1.27 его нет.
- **Журнал nginx — без строки запроса и Referer**: в них токен оверлея из ссылки
  OBS. `location` для `/legal/` — только файлы `.md`, страницы документов — SPA.
- **Umami с основного домена — только `/u/script.js` и `/u/api/send`.** Весь
  Umami по префиксу открыл бы его вход и API в обход пароля `stats.<домен>`.
  Интерфейс — на `stats` за `basic_auth`; ключи Umami из секрета приложения
  deploy.sh в окружение API не пускает. После пароля пропуск — httpOnly-cookie
  `stats_gate`: заголовок `Authorization` занят токеном самого Umami.
  Выдача cookie — внутри `route`, строго после `basic_auth`.
- **Админка — два рубежа.** `admin.<домен>` за `basic_auth` с пропуском
  `admin_gate` на весь домен, и блок `api.<домен>` без этого пропуска отвечает
  404 на `/api/admin/*` — кроме `OPTIONS`: предварительный запрос CORS cookie не
  несёт. Пароль — `ADMIN_PASSWORD` в секрете приложения; deploy.sh считает хэш
  и пропуск той же функцией, что для `stats`, и в окружение API пароль не пускает.
- **Расширения PostgreSQL — только блоком `extension` в Terraform.** Владелец базы
  в управляемом кластере их не включает: Umami на `CREATE EXTENSION pgcrypto`
  падал при старте.
- **Вебхук LiveKit снаружи закрыт в Caddy**: медиасервер ходит на внутренний
  адрес API, а открытая ручка без лимита писала бы аудит на каждую подделку.
- **Заголовки проверяются `curl -I` по пути страницы**, а не чтением конфига:
  `add_header` в `location` отменяет наследование заголовков сервера, и CSP
  не доходила до страниц с первого образа, хотя в конфиге стояла.
- `VITE_*` и `CSP_CONNECT_EXTRA` вшиваются при сборке образа. Смена адреса API требует пересборки —
  это ограничение любой статики, и лучше знать о нём здесь.
- Секреты не хранятся в образах и не коммитятся. В проде — Lockbox, ВМ читает
  его своим сервисным аккаунтом при каждой выкатке; в CI — только ключ публикации
  образов и ключ выкатки.
- **API и воркер получают одно и то же окружение** — якорем в `compose.yml` и
  одним `.env` в проде. Урезанное окружение воркера молча выключало продление
  подписки и обновление токенов площадок.
- **Миграции — отдельный образ** (`--target migrate`): в рантайм-образе нет ни
  CLI Prisma, ни npx. Образ собирается с нуля — только CLI Prisma версии из
  lockfile, схема и миграции, — а не `FROM build`: со сборочной стадией он весил
  гигабайт и грузился в реестр пять минут на каждый выпуск.
- **В стадию сборки API копируются только его пакеты** (`config`, `contracts`), а
  не `packages/` целиком. Лишний манифест в воркспейсе заставлял pnpm молча
  доустанавливать весь воркспейс перед `pnpm build` — слой на 1,1 ГБ.
- **Каждый `pnpm install` и `pnpm deploy` — с двумя cache mount**: store
  (`/pnpm/store`) и метаданные (`/root/.cache/pnpm`). Без них скачанное
  запекается в слой и уезжает в экспорт кэша сборки при каждом выпуске.
- **Образы статики собирают только своё приложение**: зависимости ставятся
  фильтром `@streamkit/${APP}...` (манифесты остальных приложений копируются, но
  не ставятся), исходники — только `apps/${APP}`. Проверки типов и `.d.ts` в
  образе нет: выпуск идёт только после зелёного CI того же коммита, а `tsc`
  занимал 13 секунд из 16 сборки дашборда. У API `tsc` остаётся — `nest build`
  компилирует им, и прод собирается так же, как `pnpm dev`.
- **pnpm в образ качается явно** (`corepack install` с повторами): corepack
  скачивает его лениво и без повторов, и один обрыв связи с npm ронял выпуск.
- `VITE_API_URL` — origin API без `/api`, пустой — «тот же хост».
- **Образы прошлых выпусков убираются В НАЧАЛЕ выкатки**, до записи любых
  файлов. `docker image prune -f` удаляет только образы без тега, а у прошлого
  выпуска тег есть — свой sha, поэтому прошлые выпуски не удалялись вообще:
  каждый оставлял на ВМ около полутора гигабайт. Через полтора десятка выпусков
  диск кончился, выкатка упала на `pull`, а следующая — уже на записи окружения
  из Lockbox, то есть раньше уборки. Удаляются только образы реестра с тегом-sha,
  кроме выкатываемого: зеркала caddy и umami помечены версиями. `docker image rm`
  без `-f` не удалит образ запущенного контейнера — предыдущий выпуск остаётся
  на диске до подъёма нового. Свободное место печатается в журнал выкатки.
- **Минуты Actions — ресурс, и каждое задание стоит минимум минуту.**
  Репозиторий приватный, на бесплатном плане 2000 минут в месяц, и GitHub
  округляет каждое задание вверх. Отсюда три решения в workflow, которые
  выглядят как упрощения, но ими не являются: типы, юнит-, интеграционные и
  сквозные тесты — одно задание `checks` (одна установка и одна сборка вместо
  трёх); безопасность и проверка инфраструктуры — одно задание; образы в CI
  собираются только в пулреквестах — на `main` их тут же собирает «Выпуск
  образов», и он же проверяет образ API trivy и копирует сторонние образы в
  `mirror/` (уже скопированные пропускает). Правка только документации
  (`docs/**`, `CLAUDE.md`, `README.md`) CI не запускает; юридические тексты в
  `apps/web/public/legal` — запускают. Workflow проверяются `actionlint` до
  пуша: на ошибку в YAML тоже уходят минуты.
- **Образы собираются одним заданием, а не матрицей** — и в CI, и в выпуске.
  Матрица из пяти заданий оплачивалась десятью минутами в пулреквесте и
  восемью в выпуске при двух-трёх минутах работы: каждое задание округлялось
  отдельно и заново собирало общую стадию `base`. Кэш у каждого образа свой
  (scope `<образ>` и `release-<образ>`), общий scope затирал бы соседей. В
  пулреквесте образы собираются, только когда правка может сломать образ, не
  сломав `pnpm build`: список путей — в шаге «Только статика?» ворот.
- **Черновик пулреквеста CI не запускает**; перевод в «готов» — запускает.
- **Кэш turbo в `checks` восстанавливается между прогонами**, поэтому тест,
  читающий файл ВНЕ своего пакета и его зависимостей, объявляет его во входах
  задачи в `turbo.json` пакета (`$TURBO_ROOT$/...`). Иначе правка этого файла
  не сбросит кэш, и тест пройдёт по старому результату — зелёным.
- **`ARG`/`ENV` сборки статики — после установки зависимостей.** ENV входит в
  ключ кэша всех следующих слоёв: адрес API выше `pnpm install` делал слой
  `node_modules` своим для каждого адреса.
- **Прод выкатывается только workflow «Выкатка»** с тегом-sha из `main`; пустой тег — последний
  выпуск, у которого собраны образы (не голова `main`: её выпуск может ещё идти,
  а выпуск после упавшего CI «успешен» с пропущенными заданиями). Руками
  на ВМ — только разбор аварии; изменения, сделанные руками, следующая выкатка
  перезапишет.

## Запуск

```bash
docker compose -f infra/docker/compose.dev.yml --env-file .env up -d
docker compose -f infra/docker/compose.yml --env-file .env up --build
```
